Load balancer design.

A C++ simulation that distributes incoming requests across a changing pool of web servers.

How requests move through the system.

02 / DESCRIPTION

How it works.

The simulation starts by reading the configuration and asking the user for the initial number of servers and the number of clock cycles to run. The load balancer creates the server pool and fills the queue with 100 accepted requests per starting server. Each request contains randomly generated incoming and outgoing IP addresses, a random positive integer processing time, and a job type: processing (P) or streaming (S).

The diagram shows the path each generated request follows. The IP range blocker checks the incoming address first. Blocked requests are rejected and counted; accepted requests enter a first-in, first-out queue. The load balancer owns the queue and server pool and assigns the oldest waiting request to an available web server. Each server handles one request at a time, advances its processing by one unit per clock cycle, and becomes available again when the request is complete. New requests arrive randomly while the simulation runs. Both job types use the same queue and server pool.

The scaling policy adjusts capacity based on the number of waiting requests. If the queue rises above 80 times the number of servers, the load balancer adds one server. If it falls below 50 times the number of servers, it removes one idle server while retaining at least one server in the pool. If all servers are busy, removal waits until one becomes idle. At either threshold boundary, the server count stays the same. After a change, the system waits a configurable number of cycles before checking again. At the requested end time, it stops and writes a summary of completed requests, remaining work, rejected requests, and server changes.
